# Updater

At launch the app checks the release feed once. When the feed names a newer version, a banner under the toolbar offers **Update now** and **Later**. Settings > About shows the installed version and has a manual **Check for updates** button. **Update now** downloads the archive, verifies its signature, waits until no build runs, backs up the database and print queue, installs, and restarts the app. Nothing installs without that click, and any failure leaves the running app as it was.

## Sub-features

- `update-banner` covers the strip under the toolbar. While an update is offered, `update-banner` has `role=status`, `update-version` reads "Materialize 3D <new> is available.", the next span reads "You have <current>.", and a "What's new" `<details>` holds `update-notes` when the feed sends notes. The buttons are `update-now` ("Update now") and `update-later` ("Later").
- `update-installing` covers the banner after the click. `update-now` reads "Updating…", both buttons are disabled, the notes are hidden, and `update-progress` reads "Downloading… <n> of <m> MB The app restarts when the update is installed." (or "Downloading… <n> MB" when the feed sends no length) or the waiting text below.
- `update-waiting` covers the wait for running builds. `update-progress` and `about-status` read "Waiting for 1 build to finish. Then the update installs and the app restarts." (or "Waiting for <n> builds to finish. ..." for more than one). The text comes from `waitingMessage` in `src/stores/updates.ts`, fed by the `update:waiting` event.
- `update-error` covers the failed state. `update-banner` then has `role=alert`. After a failed check, its heading reads "Could not check for updates." and its only button reads "Dismiss". After a failed install, the heading reads "Materialize 3D <new> did not install." and the buttons read "Try again" and "Later". In both cases `update-error` holds the backend message and the next span reads "The current version keeps running." The error buttons have no testid, so use `text=Dismiss`, `text=Try again`, or `text=Later`.
- `update-later` hides the banner for this launch only. The flag lives in the store, not the DB, so the next launch asks again. **Dismiss** on the error banner does the same. A later **Update now** from Settings > About shows the banner again, and a failed manual check shows the error banner even after **Later**.
- `about-section` covers Settings > About. `about-version` reads "Materialize 3D <version>". `about-check` reads "Check for updates", or "Checking…" while a check runs, and is disabled during a check or an install. `about-update-now` ("Update now") appears when an update is offered, and stays after a failed install. `about-status` reads "Materialize 3D is up to date.", "Version <new> is available.", "Installing the update. The app restarts when it is done.", the waiting text, or the error text with `role=alert`.

## How to get to it (user POV)

- Launch the app. When a newer version exists, the banner appears under the toolbar with no user action.
- Click the gear button in the toolbar, labelled `Settings`. About is the last section. Click **Check for updates**.

## Driving it with wd.ts

Preconditions:

- Onboarding completed per the baseline in README.md.
- A debug build. Export `M3D_E2E_UPDATE_FEED=<url of latest.json>` before `$S/m3d.sh up`. The debug binary then asks that URL instead of the GitHub release feed (`updater` in `src-tauri/src/updater.rs`). A release build never compiles the override. The override changes only the feed, so the archive must still carry a signature the build trusts.
- A local feed. Run a bun server on 127.0.0.1 that answers `/latest.json` with `version`, `notes`, `pub_date`, and `platforms["linux-x86_64"]` holding `signature` and the archive `url`, and answers that `url` with the archive bytes. For the archive, the signature, and the version, use `ARCHIVE`, `ARCHIVE_SIG`, and `SIGNED_VERSION` from the tests in `src-tauri/src/updater.rs`. Do not copy them into a tracked file. To offer no update, announce a `version` no higher than the running one.
- To let the install verify, make the build trust the key that signed that archive. Export `TAURI_CONFIG='{"plugins":{"updater":{"pubkey":"<KEY_A>"}}}'` before `up`, with the value of `KEY_A` from the same tests. It is a throwaway key whose private half was never kept. `cargo build` embeds it, so set the variable before the build and confirm it with `grep -c <40 characters from the middle of KEY_A> src-tauri/target/debug/materialize-3d`, which prints `1`. Every minisign key starts with the same prefix, so a slice from the start proves nothing. Without it the build trusts the release key, and the download is rejected.
- For the waiting state, a slicer that takes long enough. Export `BAMBU_STUDIO_CLI` to a wrapper script that passes `--help` straight to the real Bambu Studio `AppRun` and sleeps about 60 seconds before any other command, and export `BAMBU_STUDIO_PROFILES` to the real `resources/profiles/BBL` folder. Then a sign build per [signs](./signs.md) stays in `building` long enough to click **Update now**.

- **Banner at launch (observed 2026-11-01).** With the feed announcing 9.9.9, run `$S/wd.ts wait "[data-testid=update-banner]" 30000`. `$S/wd.ts text "[data-testid=update-version]"` reads "Materialize 3D 9.9.9 is available.", and `$S/wd.ts text "[data-testid=update-now]"` reads "Update now".
- **Notes (observed 2026-11-01).** Run `$S/wd.ts click "[data-testid=update-banner] summary"`. The `text=` form fails on the apostrophe in "What's new". `$S/wd.ts text "[data-testid=update-notes]"` reads the feed's `notes`.
- **Later (observed 2026-11-01).** Run `$S/wd.ts click "[data-testid=update-later]"` and `$S/wd.ts gone "[data-testid=update-banner]"`. Relaunch with `$S/wd.ts end` and `$S/wd.ts session`. Onboarding is already done, so `$S/wd.ts wait "[data-testid=update-banner]" 30000` finds the banner again.
- **About with an update offered (observed 2026-11-01).** Open Settings per [settings](./settings.md), then run `$S/wd.ts wait "[data-testid=about-section]"` and `$S/wd.ts hover "[data-testid=about-section]"` to scroll it into view. `about-version` reads "Materialize 3D 0.2.1" (the version in `src-tauri/tauri.conf.json`), `about-status` reads "Version 9.9.9 is available.", and `$S/wd.ts count "[data-testid=about-update-now]"` prints `1`.
- **Up to date (observed 2026-11-01).** With the feed announcing a version no higher than the running one, click `[data-testid=about-check]`. `about-status` reads "Materialize 3D is up to date." and `about-update-now` is gone.
- **Failed check (observed 2026-11-01).** With no server on the feed port, click `[data-testid=about-check]`. `about-status` reads "Could not check for updates: error sending request for url (<feed url>)" and has `role=alert`. The banner shows the same failure at once: `update-banner` has `role=alert`, its `strong` heading reads "Could not check for updates.", `update-error` holds the same message, and `text=Dismiss` hides it. A launch with the feed down shows that same banner.
- **Rejected signature (observed 2026-11-01).** On a build without `TAURI_CONFIG`, click `[data-testid=update-now]` or `[data-testid=about-update-now]`. The banner turns into the alert, its heading reads "Materialize 3D 9.9.9 did not install.", `update-error` reads "The update did not download or its signature did not verify: The signature was created with a different key than the one provided", and the buttons read "Try again" and "Later". `about-status` shows the same message with `role=alert`, and `about-update-now` stays. The app keeps running, `DB` has no `backups` folder beside it, and the binary is still an ELF file. `text=Try again` fails the same way, and `text=Later` hides the banner.
- **Waiting for a build (observed 2026-11-01).** On a build that trusts `KEY_A`, with the slow slicer, start a sign build from a spec and wait for `[data-testid=build-progress]`. Click `[data-testid=update-now]`. `$S/wd.ts wait 'xpath=//*[@data-testid="update-progress"][contains(., "Waiting for 1 build")]' 10000` succeeds, and `update-progress` reads "Waiting for 1 build to finish. Then the update installs and the app restarts." Open Settings, and `about-status` reads the same, with `about-check` disabled. `update-now` reads "Updating…" and is disabled. The `builds` table in `DB` has no row yet, because the build is recorded when it ends.
- **Install and restart (observed 2026-11-01).** When the build ends, `builds` gains a `verified` row, `<data>/backups/0.2.1-to-9.9.9-<time>/` appears beside `DB` with `materialize.db` (and `print_queue.json` when a queue file exists), and the install writes the archive over the binary within 100 ms of the row. On Linux the test archive is not a runnable app, so the restart fails and the WebDriver session ends with "session deleted because of page crash or hang". That is the expected end of the run. The sign build calls the slicer twice, so the 60 second wrapper holds the install for about 2 minutes.

## Gotchas

- The check runs once per launch from `checkForUpdatesAtLaunch` in `src/App.tsx`. A second check needs **Check for updates** in About or a relaunch.
- A feed announcing the running version or lower gives "up to date". Only a higher version counts.
- `M3D_E2E_UPDATE_FEED` and `TAURI_CONFIG` are read by the process that `up` starts, so export them before `up`. `TAURI_CONFIG` takes effect through the build. `up` rebuilt the binary in about 10 seconds when the variable changed, in both directions **(observed 2026-11-01)**. `m3d.sh doctor` cannot tell which key the binary trusts, so use the `grep -c` check above.
- A successful install on Linux writes the archive over `src-tauri/target/debug/materialize-3d`. Delete that file before the next `up` so `cargo build` makes a real binary again. `file src-tauri/target/debug/materialize-3d` tells the two apart.
- The install closes the build gate until the restart. A build asked for during that window fails with "an update is installing and the app is about to restart. Build again after it restarts." A failed install reopens the gate.
- The same waiting state shows in both places. The banner text is in `update-progress`, not in `update-banner` as a whole, so match on `update-progress`.
- The macOS release path, with a real signed archive, backup check, and restart acceptance, is separate from this Linux debug recipe. See [Verify the installed Mac app](../../../../docs/verify-on-mac.md).
