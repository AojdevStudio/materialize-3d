# Updater

At launch the app checks the release feed once. When the feed names a newer version, a banner at the top of the chat column offers **Update now** and **Later**. **Update now** downloads the archive, verifies its signature, waits until the agent's work is done, backs up the database and print queue, installs, and restarts the app. Nothing installs without that click, and any failure leaves the running app as it was.

## Sub-features

- `update-banner` covers the strip at the top of the chat column. While an update is offered, `update-banner` has `role=status`, `update-version` reads "Materialize 3D <new> is available.", the next span reads "You have <current>.", and a "What's new" `<details>` holds `update-notes` when the feed sends notes. The buttons are `update-now` ("Update now") and `update-later` ("Later").
- `update-installing` covers the banner after the click. `update-now` reads "Updating…", both buttons are disabled, the notes are hidden, and `update-progress` reads "Downloading… The app restarts when the update is installed." until the first progress event, then "Downloading… <n> of <m> MB The app restarts when the update is installed." (or "Downloading… <n> MB The app restarts when the update is installed." when the feed sends no length) or the waiting text below.
- `update-waiting` covers the wait for the agent's work. A turn that runs, and a slice Rust runs for it, each hold the update off. `update-progress` reads "Waiting for 1 build to finish. Then the update installs and the app restarts." (or "Waiting for <n> builds to finish. ..." for more than one). The text comes from `waitingMessage` in `src/stores/updates.ts`, fed by the `update:waiting` event.
- `update-error` covers the failed state. `update-banner` then has `role=alert`. After a failed check, its heading reads "Could not check for updates." and its only button reads "Dismiss". After a failed install, the heading reads "Materialize 3D <new> did not install." and the buttons read "Try again" and "Later". A failed backup stops the install with "Did not update, because the backup failed: <reason>". An install that fails after the backup ends its message with "Your data was backed up to <dir> first." In both cases `update-error` holds the backend message and the next span reads "The current version keeps running." The error buttons have no testid, so use `text=Dismiss`, `text=Try again`, or `text=Later`.
- `update-later` hides the banner for this launch only. The flag lives in the window, so the next launch asks again. **Dismiss** on the error banner does the same.

## How to get to it (user POV)

- Launch the app. When a newer version exists, the banner appears at the top of the chat column with no user action.

## Driving it with wd.ts

Preconditions:

- A debug build. Export `M3D_E2E_UPDATE_FEED=<url of latest.json>` before `$S/m3d.sh up`. The debug binary then asks that URL instead of the GitHub release feed (`updater` in `src-tauri/src/updater.rs`). A release build never compiles the override. The override changes only the feed, so the archive must still carry a signature the build trusts.
- A local feed. Run a bun server on 127.0.0.1 that answers `/latest.json` with `version`, `notes`, `pub_date`, and `platforms["linux-x86_64"]` holding `signature` and the archive `url`, and answers that `url` with the archive bytes. For the archive, the signature, and the version, use `ARCHIVE`, `ARCHIVE_SIG`, and `SIGNED_VERSION` from the tests in `src-tauri/src/updater.rs`. Do not copy them into a tracked file. To offer no update, announce a `version` no higher than the running one.
- To let the install verify, make the build trust the key that signed that archive. Export `TAURI_CONFIG='{"plugins":{"updater":{"pubkey":"<KEY_A>"}}}'` before `up`, with the value of `KEY_A` from the same tests. It is a throwaway key whose private half was never kept. `cargo build` embeds it, so set the variable before the build and confirm it with `grep -c <40 characters from the middle of KEY_A> src-tauri/target/debug/materialize-3d`, which prints `1`. Every minisign key starts with the same prefix, so a slice from the start proves nothing. Without it the build trusts the release key, and the download is rejected.
- The feed server can read `ARCHIVE` and `ARCHIVE_SIG` from `src-tauri/src/updater.rs` at start and serve the announced version from a file, so one server covers every state: write `9.9.9` or `0.0.1` to the file, or stop the server for the failed check **(observed 2026-11-03)**. Keep it as a scratch file outside the checkout.

- **Banner at launch (observed 2026-11-01, again 2026-11-03).** With the feed announcing 9.9.9, run `$S/wd.ts wait "[data-testid=update-banner]" 30000`. `update-banner` has `role=status`, `$S/wd.ts text "[data-testid=update-version]"` reads "Materialize 3D 9.9.9 is available.", the next span reads "You have 0.2.2.", and `$S/wd.ts text "[data-testid=update-now]"` reads "Update now".
- **Notes (observed 2026-11-01).** Run `$S/wd.ts click "[data-testid=update-banner] summary"`. The `text=` form fails on the apostrophe in "What's new". `$S/wd.ts text "[data-testid=update-notes]"` reads the feed's `notes`.
- **Later (observed 2026-11-01, again 2026-11-03).** Run `$S/wd.ts click "[data-testid=update-later]"` and `$S/wd.ts gone "[data-testid=update-banner]"`. Relaunch with `$S/wd.ts end` and `$S/wd.ts session`. `$S/wd.ts wait "[data-testid=update-banner]" 30000` finds the banner again.
- **Up to date.** With the feed announcing a version no higher than the running one, relaunch. No banner shows.
- **Failed check (observed 2026-11-01, again 2026-11-03).** Launch with no server on the feed port. `update-banner` has `role=alert`, its `strong` heading reads "Could not check for updates.", `update-error` holds "Could not check for updates: error sending request for url (<feed url>)", and `text=Dismiss` hides it.
- **Rejected signature (observed 2026-11-01).** On a build without `TAURI_CONFIG`, click `[data-testid=update-now]`. The banner turns into the alert, its heading reads "Materialize 3D 9.9.9 did not install.", `update-error` reads "The update did not download or its signature did not verify: The signature was created with a different key than the one provided", and the buttons read "Try again" and "Later". The app keeps running, and the binary is still an ELF file. `text=Try again` fails the same way, and `text=Later` hides the banner.
- **Waiting for a turn.** From the code, not a run. On a build that trusts `KEY_A`, send a request in the studio and click `[data-testid=update-now]` while `[data-testid=working]` shows. `update-progress` reads "Waiting for 1 build to finish. Then the update installs and the app restarts." until the turn ends. A turn needs an inference login, see [studio](./studio.md).
- **Install and restart (observed 2026-11-01, again 2026-11-03).** With nothing running, click `[data-testid=update-now]`. `<data>/backups/0.2.2-to-9.9.9-<time>/` appears with `materialize.db`, and the install writes the archive over the binary. On Linux the test archive is not a runnable app, so the restart fails and the WebDriver session ends with "session deleted because of page crash or hang". That is the expected end of the run.

## Gotchas

- The check runs once per launch from `checkForUpdatesAtLaunch` in `src/studio/StudioApp.tsx`. A second check needs a relaunch.
- A feed announcing the running version or lower gives "up to date". Only a higher version counts.
- `M3D_E2E_UPDATE_FEED` and `TAURI_CONFIG` are read by the process that `up` starts, so export them before `up`. `TAURI_CONFIG` takes effect through the build. `up` rebuilt the binary in about 10 seconds when the variable changed, in both directions **(observed 2026-11-01)**. `m3d.sh doctor` cannot tell which key the binary trusts, so use the `grep -c` check above.
- A successful install on Linux writes the archive over `src-tauri/target/debug/materialize-3d`. Delete that file before the next `up` so `cargo build` makes a real binary again. `file src-tauri/target/debug/materialize-3d` tells the two apart.
- The install closes the update gate until the restart. A send asked for during that window is refused with "An update is installing, and the app restarts when it is done. Send this again after it opens." A failed install reopens the gate. The Linux debug run cannot hold that window open, so this is confirmed from `src-tauri/src/sidecar.rs` and its tests, not live.
- The macOS release path, with a real signed archive, backup check, and restart acceptance, is separate from this Linux debug recipe. See [Verify the installed Mac app](../../../../docs/verify-on-mac.md).
